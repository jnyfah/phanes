Step 1: raw io_uring, no liburing
The mental model: you and the kernel share two ring buffers in memory. You write requests into one, the kernel writes results into the other. Three syscalls total, and they aren't even in glibc — you call them by number.


#include <linux/io_uring.h>
#include <sys/syscall.h>
#include <sys/mman.h>
#include <unistd.h>

// The 3 syscalls have no glibc wrappers — you invoke them raw.
static int io_uring_setup(unsigned entries, struct io_uring_params* p) {
    return (int)syscall(__NR_io_uring_setup, entries, p);
}
static int io_uring_enter(int fd, unsigned to_submit, unsigned min_complete, unsigned flags) {
    return (int)syscall(__NR_io_uring_enter, fd, to_submit, min_complete, flags, NULL, 0);
}
Setup — ask the kernel for rings, then mmap them into your address space:


struct io_uring_params p = {0};
int ring_fd = io_uring_setup(8, &p);   // 8 = queue depth

// The submission ring and completion ring. On modern kernels they share
// one mmap region (IORING_FEAT_SINGLE_MMAP), but classically it's two.
void* sq_ptr = mmap(0, p.sq_off.array + p.sq_entries * sizeof(unsigned),
                    PROT_READ|PROT_WRITE, MAP_SHARED|MAP_POPULATE,
                    ring_fd, IORING_OFF_SQ_RING);

void* cq_ptr = mmap(0, p.cq_off.cqes + p.cq_entries * sizeof(struct io_uring_cqe),
                    PROT_READ|PROT_WRITE, MAP_SHARED|MAP_POPULATE,
                    ring_fd, IORING_OFF_CQ_RING);

// The actual SQE array (where you fill in requests) is a third mapping.
struct io_uring_sqe* sqes = mmap(0, p.sq_entries * sizeof(struct io_uring_sqe),
                    PROT_READ|PROT_WRITE, MAP_SHARED|MAP_POPULATE,
                    ring_fd, IORING_OFF_SQES);
Those p.sq_off.* / p.cq_off.* are byte offsets the kernel hands back telling you where the head/tail indices live inside the mapped region. You compute pointers to them once:


unsigned* sq_tail   = sq_ptr + p.sq_off.tail;
unsigned* sq_array  = sq_ptr + p.sq_off.array;
unsigned  sq_mask   = *(unsigned*)(sq_ptr + p.sq_off.ring_mask);

unsigned* cq_head   = cq_ptr + p.cq_off.head;
unsigned* cq_tail   = cq_ptr + p.cq_off.tail;
unsigned  cq_mask   = *(unsigned*)(cq_ptr + p.cq_off.ring_mask);
struct io_uring_cqe* cqes = cq_ptr + p.cq_off.cqes;
Submit one read:


unsigned idx = *sq_tail & sq_mask;
struct io_uring_sqe* sqe = &sqes[idx];
memset(sqe, 0, sizeof(*sqe));
sqe->opcode    = IORING_OP_READ;
sqe->fd        = file_fd;
sqe->addr      = (unsigned long)buffer;
sqe->len       = buffer_size;
sqe->off       = 0;                 // file offset
sqe->user_data = 42;                // YOUR tag — comes back in the completion

sq_array[idx] = idx;
// release-store the tail so the kernel sees the SQE before the bumped tail
__atomic_store_n(sq_tail, *sq_tail + 1, __ATOMIC_RELEASE);

io_uring_enter(ring_fd, 1, 1, IORING_ENTER_GETEVENTS);  // submit 1, wait for 1
Reap the completion:


unsigned head = __atomic_load_n(cq_head, __ATOMIC_ACQUIRE);
struct io_uring_cqe* cqe = &cqes[head & cq_mask];
// cqe->user_data == 42  → which request this was
// cqe->res             → bytes read, or -errno
__atomic_store_n(cq_head, head + 1, __ATOMIC_RELEASE);  // tell kernel we consumed it
That's a complete round trip. The only genuinely tricky part is the acquire/release pairing on those head/tail indices — and that's the exact same memory-ordering reasoning you already wrote by hand in deque.cpp. The tail is a release store, the head you read is an acquire load. You've done this before; it's the same muscle.

The batching payoff: to submit 1000 sample reads, you fill 1000 SQEs in a loop, bump the tail once, and call io_uring_enter(ring_fd, 1000, 1000, ...) — one syscall for a thousand reads, versus your current thousand pread syscalls. Then drain 1000 completions, each tagged with which file it was.

Each milestone is a standalone thing you build in experiments/uring_hello.cpp (throwaway, raw, no abstraction), runs end-to-end, and teaches one concept. Don't move on until the current one works and you understand why. You only graduate to src/io/uring.cpp at the very end.

M1 — One read, queue depth 1.
Open a file, push a single IORING_OP_READ SQE, io_uring_enter, reap one CQE, print the bytes.
Learn: the full setup (io_uring_setup, the three mmaps, the offset structs), and the head/tail index dance for exactly one entry.
Done when: it prints the first N bytes of a real file correctly.

M2 — Make it robust.
Handle the ugly truths of one read: cqe->res < 0 is -errno, cqe->res < len is a short read (you got fewer bytes than asked — totally normal, not an error), and you must always advance the CQ head after consuming.
Learn: completion semantics — the single biggest source of "why is my data wrong" bugs.
Done when: it correctly handles a 10-byte file, an empty file, and a nonexistent fd without lying or crashing.

M3 — Many reads in flight (the whole point).
Submit several reads at once — different files, or different offsets of one file — with one io_uring_enter, then reap all completions as they arrive.
Learn: batch submission, and that completions come back out of order — the disk returns whatever's ready first.
Done when: you fire 5 reads in one syscall and collect 5 results regardless of arrival order.

M4 — Correlation via user_data.
Stamp each SQE's user_data with a tag (e.g. an index into your file list). On completion, use cqe->user_data to know which read finished.
Learn: the tag is the entire mechanism that makes async usable — without it, out-of-order completions are meaningless.
Done when: you can submit reads for files A,B,C and correctly attribute each completion back to its file.

M5 — Backpressure / bounded depth.
The ring has a fixed size (say 32). If a group has 5,000 files you cannot submit all at once. Build the submit→reap→submit-more loop that keeps the ring full but never overflows it.
Learn: queue-depth management — the difference between a toy and something that handles real directories.
Done when: it processes a directory of hundreds of files with a depth-32 ring without dropping or overflowing.

M6 — Wire in the hash.
Read a file's three samples through the ring and feed them to phanes_hash_update (same hash your current sample_hash_file uses). Verify the hash matches the current pread-based version bit-for-bit on the same file.
Learn: integrating the ring with real downstream work, and a correctness anchor — your io_uring path must produce identical hashes to today's path.
Done when: ring-hash == pread-hash for a set of test files.

M7 — Graduate to src/io/uring.cpp.
Now — and only now — wrap what you've learned behind the IoRing class in io.ixx (the submit/reap/wait PIMPL we discussed). Plug it into a copy of sample_hash_file behind a build flag.
Learn: turning experiment knowledge into a clean module interface.
Done when: bench_duplicates runs against both paths and tells you which is faster — your proof it was worth it.

M8 — Then, and only then, start the Windows ioring.cpp and let the shared interface fall out of having two real backends.

The one mindset note
Through M1–M5 you'll be tempted to "make it general." Don't. Hardcode the filename, hardcode depth, leak fds — it's a learning scaffold. Generality is M7's job, after the kernel interface is muscle memory. The fear you started with dies somewhere around M3, when you watch five reads come back out of order and realize you're driving the kernel directly.
