

The layout

src/io/
├── io.ixx          ← module interface — the ONE cross-platform API
├── io_linux.cpp    ← io_uring backend   (compiled only on Linux)
└── io_windows.cpp  ← IoRing backend     (compiled only on Windows)
The trick that keeps this clean: the platform split lives in the .cpp files, never in the interface. io.ixx declares a platform-agnostic API — IoRequest, IoCompletion, an IoRing class with submit/reap/wait. The rest of phanes just writes import phanes.io; and never sees a single #ifdef. Then CMake picks which .cpp actually gets compiled based on the OS. Only one backend is ever in the build.

So io.ixx is pure declaration:

Since you said you won't jump into code yet — for step 1 (learning io_uring at all), don't put it in src/io/ and don't make it a module. Make a throwaway:


experiments/uring_hello.cpp   ← plain .cpp, plain main(), gitignored or scratch
Compile it by hand (g++ -std=c++23 uring_hello.cpp -o hello), read a file, print bytes. Modules + CMake + PIMPL all add friction you don't want while you're still fighting the kernel API for the first time. Learn the API naked first; the src/io/ module is where it graduates to once you understand it.

The worker thread blocks in next() waiting for the next completion. But it has nothing else to do — it already submitted the whole group; now it just consumes results.
While this thread waits, other worker threads run other groups. That's your parallelism — the thread pool.
The ring gives you I/O concurrency within a group (many reads in flight); the pool gives you parallelism across groups. Two different axes, both covered. No coroutine needed.
